# toolsmith — 마스터 도구 목록 (단일 진실원천)

> 이 파일이 "무엇을 만들 것인가"의 유일한 기준이다. 새 세션은 여기부터 읽는다.
> 도구를 하나 끝낼 때마다 **상태**를 갱신한다. 상태는 `미착수 → 구현 → QA → 배포`.

## 원칙 (바꾸지 말 것)

1. **서버 연산 0.** v1의 모든 처리는 브라우저 안에서 끝난다. 업로드가 없다.
2. **무거운 자산은 Vercel에 두지 않는다.** AI 모델은 HuggingFace CDN, wasm 바이너리는 R2/jsDelivr.
   Vercel(Pro, 월 1TB)에는 앱 셸만. 근거: 모델 100MB × 방문 1만 = 1TB.
3. **버튼을 누르기 전엔 아무것도 다운로드하지 않는다.** 모든 무거운 모듈은 지연 로딩.
4. **3단 폴백.** WebGPU → WASM(CPU) → 명확한 미지원 안내. 조용한 실패 금지.
5. **카피레프트 금지.** AGPL/GPL 라이브러리는 채택하지 않는다 (아래 라이선스 지뢰 참조).
6. **메인 스레드에서 처리하지 않는다.** 전부 Web Worker.

## 층 구조와 각 층의 역할

| 층 | 런타임 | 역할 | 원가 |
|---|---|---|---|
| **Tier 1** | WASM / 브라우저 네이티브 (CPU) | **SEO 트래픽**. 전 기기(모바일 포함) 동작 | 0 |
| **Tier 2** | WebGPU | **차별화·재방문**. 데스크톱 한정 | 0 |
| **Tier 3** | WebGPU (Lab) | **백링크·소셜**. 화제성 전용, 실용성 무관 | 0 |
| (유료, 보류) | 4080 노트북 서버 | 긴 파일·대형 모델·배치·모바일 | GPU 시간 |

유료층은 **Tier 1~2가 실제 유입을 만든 뒤에만** 착수한다. v1에서는 4080을 쓰지 않는다.

## 채택하지 않기로 한 것 (재논의 금지)

| 대상 | 이유 |
|---|---|
| **ffmpeg.wasm (@ffmpeg/core)** | **GPL 빌드다.** 실측(2026-07-26): `ffmpeg-core.wasm` 안에 박힌 빌드 설정이 `--enable-gpl --enable-libx264 --enable-libx265`. libx264/x265 를 링크한 결과물은 GPL 이 되고, 30.7MB 바이너리를 브라우저에 보내는 것은 배포에 해당한다 → 사이트 전체가 GPL 이 된다. 표에 "LGPL/MIT" 로 적혀 있던 것은 **검증 전 기재였고 사실이 아니었다.** LGPL 빌드를 직접 만들면 쓸 수 있지만 그때도 H.264 인코딩은 빠진다 |
| **briaai/RMBG-1.4** | 배경 제거로 검색하면 제일 먼저 나오는 모델이고 품질도 좋지만 **비상업** 라이선스다. 모델 카드가 직접 이렇게 적는다 — "The model is released under a Creative Commons license for non-commercial use… Commercial use is subject to a commercial agreement with BRIA." 코드가 아니라 **가중치**에 걸린 제약이라 우회할 방법이 없다. RMBG-2.0 은 더 엄하다 |
| **MODNet** | CC BY-NC-SA 4.0. NC 도 SA 도 우리에게 맞지 않는다 |
| **TranslateGemma 4B** | 이 문서가 #16 의 후보로 적어 두었던 모델인데 **쓸 수 없다.** 원본 `google/translategemma-4b-it` 는 **수동 승인 게이트**(`gated: manual`)이고, Gemma 약관은 가중치를 받는 쪽에도 사용 제한을 그대로 넘기라고 요구한다 — 익명의 방문자 브라우저에 2.7GB 를 흘려보내는 방식으로는 지킬 수 없는 조건이다. ONNX 미러가 게이트 없이 열려 있지만, **배포하는 당사자는 우리**다. 크기도 최소 2.7GB(q4f16)로 자막 생성의 18배 |
| **NLLB-200 distilled 600M** | 번역 품질 대비 크기가 가장 좋은 후보지만 **CC-BY-NC-4.0**. RMBG-1.4 와 같은 이유로 탈락 |
| **opus-mt 다국어판(`en-mul`)** | Apache-2.0 에 112MB 로 가장 싸다. 그런데 **한국어가 아예 안 나온다** — ">>kor<< The meeting starts at three" 에 ".. hlanganning starting at three"(줄루어)를 돌려줬다. **싸고 틀린 것은 후보가 아니다** |
| **@imgly/background-removal** | 편하지만 AGPL-3.0. 규칙 6 |
| Ghostscript.wasm | **AGPL** — 네트워크 배포 시 전체 소스 공개 의무. 상용 불가 |
| mupdf-wasm | AGPL, 동일 |
| mediabunny | MPL-2.0. 약한 카피레프트라 실무 위험은 낮지만, MIT/BSD 조합(mp4box + mp4-muxer + webm-muxer)으로 같은 일이 되므로 굳이 들이지 않는다 |
| LibreOffice WASM (문서 변환) | 2026년에도 너무 크고 느리고 불안정. 문서 변환은 v1 범위 밖 |
| 브라우저 챗봇 (Gemma/Qwen/GPT-OSS) | 차별화 0, 다운로드만 큼. 도구 사이트와 무관 |

## 다국어 (2026-07-25 결정, 재논의 금지)

- **en · ko · ja · es · de · pt-br** 6개. 근거: en 은 검색량과 LLM 인용의 기본값,
  es·pt-BR 은 화자 수 대비 변환 도구 경쟁이 느슨하고, ja 는 유료 전환율이 높으며,
  de 는 구매력이 가장 크다. zh 는 구글 점유율이 낮아 제외, id·hi 는 트래픽 대비 단가가
  낮아 보류.
- URL 은 **전 언어 접두사**(`/en/...`, `/ko/...`). 기본 언어라고 접두사를 빼지 않는다 —
  한 언어만 규칙이 다르면 색인·링크 실수가 거기서 난다. `/` 는 정적 언어 선택 페이지,
  x-default 는 `/en`.
- 새 도구를 만들 때 6개 언어 사전을 **함께** 채운다. 영어로 새는 것은
  `tests/i18n.spec.ts` 가 잡는다.

## 분석(GA4)

- 속성 **Toolsmith**, 측정 ID `G-V1SX1J2BG2`. `NEXT_PUBLIC_GA_ID` 가 없으면 태그를 심지
  않는다 — 로컬·프리뷰 클릭이 프로덕션 통계를 더럽히지 않게.
- **향상된 측정의 "파일 다운로드" 는 반드시 꺼 둔다.** 이 항목은 클릭된 다운로드 링크의
  이름을 GA 로 보내는데, 우리 결과 파일 이름에는 사용자의 원본 파일명이 들어간다
  (`보고서-추출.pdf`). "파일이 기기를 떠나지 않는다" 는 약속이 바로 여기서 깨진다.
  새 스트림을 만들 때마다 확인할 것 — 기본값이 **켜짐**이다.
- **전환 이벤트는 `tool_completed`** 하나다. 도구가 결과를 만들어 낸 순간 보내고,
  실리는 것은 `tool_slug`(도구 이름) 뿐이다. 파일명·크기·페이지 수는 넣지 않는다 —
  파일명에는 사용자의 사정이 그대로 들어 있고, 크기와 쪽수도 모이면 문서를 지목하는
  실마리가 된다.
- `@next/third-parties` 의 `sendGAEvent` 는 쓰지 않는다. dataLayer 에 넣기는 하는데
  gtag.js 가 집어가지 않았다(실측: `gtm.uniqueEventId` 가 붙지 않고 collect 요청도
  나가지 않음). 태그가 정의한 **`window.gtag` 를 직접 부른다.**
- **GA4 는 이벤트를 모아 보낸다.** 테스트에서 고정 대기(3초)로는 놓친다 →
  `expect.poll` 로 기다린다. "파일명이 없다" 를 검사할 때도 먼저 전환 이벤트가
  도착한 것을 확인한 뒤에 본다(양성 대조). 아무것도 안 온 상태의 "없음"은 아무 증명도 아니다.

## 영상·오디오는 WebCodecs 로 간다 (2026-07-26 결정)

ffmpeg.wasm 이 GPL 이라 못 쓰게 되면서 방향을 바꿨고, 결과적으로 이 프로젝트 규칙에 더 잘 맞는다.

- **다운로드 0MB.** ffmpeg.wasm 은 30.7MB 였다. 규칙 2·5 를 애초에 어길 일이 없다.
- **COEP 불필요.** SharedArrayBuffer 를 쓰지 않으므로 헤더 스코프 문제 자체가 사라진다.
- **하드웨어 가속.** 실측(2026-07-26, 테스트 Chromium): 인코더 H.264(baseline·main)·VP8·
  VP9·AV1, 오디오 AAC·Opus 전부 지원.
- 대가: **입력 컨테이너를 직접 열어야 한다.** MP4/MOV 는 mp4box.js(BSD-3)로 demux 하고,
  출력은 mp4-muxer/webm-muxer(MIT)로 쓴다. AVI·MKV 같은 입력은 받지 않는다 —
  **받는 척하지 말고 목록에서 빼는 쪽이 이 프로젝트의 방식이다.**
- 브라우저 지원이 이미지·PDF 도구보다 좁다(Firefox 130+, Safari 16.4+).
  `VideoEncoder.isConfigSupported` 로 실제 능력을 물어 목록을 만든다.
- **AAC 의 `description` 은 esds 박스가 아니라 그 안의 AudioSpecificConfig 다.**
  avcC 는 박스 payload 가 곧 디코더 설정이라 헤더 8바이트만 떼면 되지만, esds 는
  ES_Descriptor 가 겹겹이 싸인 구조다. 같은 방법을 쓰면 만들어진 M4A 가
  `Unable to decode audio data` 로 거절당한다 — **소리가 안 나는 파일을 내주게 된다.**
  mp4box 가 파싱해 둔 값을 쓰고, 없으면 2바이트를 직접 조립한다(`describeAac`).
- **GIF 는 인코더가 필요 없다.** 색 줄이기와 GIF 조립은 gifenc(MIT, 20KB)가 JS 로 한다.
  그래서 능력 판정도 `VideoEncoder` 가 아니라 **`VideoDecoder`** 로 물어야 한다
  (`canRunGifTools`). 인코더로 물으면 H.264 인코더가 없는 기기에서 멀쩡한 도구를
  "못 한다" 고 잘못 막는다.

## GIF 는 1/100초 격자 위에서만 움직인다 (2026-07-26)

GIF89a 는 프레임 지연을 **1/100초 단위 정수**로만 적는다. 임의의 fps 를 담을 수 없다.

- 20 · 10 · 5 fps 는 딱 떨어진다(5 · 10 · 20 칸). **15fps 는 7칸 = 14.29fps 가 된다.**
- 그래서 `lib/video/gif-timing.ts` 가 그 반올림을 **한 곳에 모은다.** 워커와 UI 가 같은
  함수를 부르므로 화면의 숫자와 파일 안의 숫자가 어긋날 수 없다. 요청값과 실제값이
  다를 때만 "실제로는 14.3 fps" 를 덧붙인다 — 규칙 3의 GIF 판.
- 2칸(50fps) 미만은 브라우저마다 10칸으로 바꿔 버리므로 하한을 2칸으로 둔다.
- **400프레임 상한.** 넘으면 버튼을 막고 이유를 말한다. GIF 는 움직임 압축이 없어
  길이가 곧 용량이다 — 30초짜리는 수십 MB 가 되고 브라우저가 먼저 무너진다.
- 프레임을 **모아 두지 않는다.** 디코더가 프레임을 내놓는 그 자리에서 양자화해 스트림에
  흘린다. 480×270 400장을 ImageData 로 쥐면 200MB 다.
- 색표는 **프레임마다 새로 뽑는다**(첫 장은 전역 색표, 나머지는 지역 색표). 장면이 바뀌어도
  색이 무너지지 않는 대신 프레임당 768바이트를 더 쓴다 — 그만한 값어치가 있다.

## 트림은 코덱을 아예 부르지 않는다 (2026-07-26)

샘플을 골라 다시 mux 할 뿐이라 **WebCodecs 가 필요 없다.** 화질이 그대로이고, 90KB 짜리
6초 영상이 1초도 안 걸린다. 대신 시간축을 정확히 다루는 일이 전부인데, 여기서 두 번 데었다.

- **mp4-muxer 의 `timestamp` 인자는 표시 시각(cts)이다.** 내부에서
  `dts = timestamp − compositionTimeOffset` 으로 되짚는다(빌드 소스 1645행).
  여기에 dts 를 넘기면 dts 가 두 번 빠져 뒤로 흐르고
  `Timestamps must be monotonically increasing (DTS went from 0 to -0.33)` 로 죽는다.
  **B프레임이 없는 파일에서는 cto 가 0 이라 이 실수가 전혀 드러나지 않는다** —
  그래서 픽스처에 `-bf 2` 를 일부러 넣었다.
- **`firstTimestampBehavior` 는 `cross-track-offset` 이어야 한다.** `strict` 는 첫 dts 가
  음수(B프레임이면 정상이다)라고 던지고, `offset` 은 트랙마다 제각각 당겨서
  **소리와 그림을 어긋나게 만든다.** 두 트랙을 같은 양만큼 옮기는 것은 이것뿐이다.
- **B프레임이 있는 파일은 cts 가 0 에서 시작하지 않는다.** 인코더가 재정렬 지연(보통
  2프레임)만큼 전체를 밀고 edit list 로 그만큼 잘라내라고 적어 둔다. 플레이어는 그 지시를
  따르므로 사용자에게는 0 초부터 보인다. 원본 cts 를 그대로 쓰면 **미리보기의 재생 위치
  (0 기준)와 우리 키프레임 좌표(0.133 기준)가 어긋나** 사용자가 찍은 지점보다 한 GOP 앞에서
  잘린다. `readMp4` 가 트랙마다 자기 최솟값을 빼서(`rebase`) 이 문제를 뿌리에서 없앤다 —
  edit list 를 지키는 것과 같은 효과이고, 길이도 샘플에서 다시 잰다.
- **정직함이 이 도구의 기능이다.** 자를 수 있는 지점은 키프레임뿐이므로 요청 지점 앞의
  키프레임으로 내리고, **버튼을 누르기 전에** "2.5초가 아니라 2.0초에서 잘립니다" 라고
  말한다. 그러려면 `inspect` 가 키프레임 목록을 UI 로 넘겨야 한다.
- QA 가 "재인코딩하지 않는다" 를 **픽셀로** 증명한다. 잘라 낸 첫 프레임과 원본의 그 프레임을
  같은 디코더에 넣어 가로 한 줄을 비교한다 — 같은 부호화 데이터이므로 최대 오차 0 이어야
  한다. 다시 인코딩했다면 손실 압축을 한 번 더 거쳐 값이 흔들린다.

## 변환은 두 갈래이고 성격이 정반대다 (2026-07-26)

한 도구 안에 완전히 다른 두 경로가 있다. **그래서 UI 가 어느 쪽인지 누르기 전에 말한다.**

- **MOV → MP4 는 재mux 다.** `.mov` 와 `.mp4` 는 라벨만 다른 같은 ISOBMFF 상자이고,
  아이폰 `.mov` 안에는 이미 H.264/HEVC + AAC 가 들어 있다. 전부 MP4 에도 그대로 들어가므로
  코덱을 한 번도 부르지 않는다. 무손실이고 순식간이다. 트림이 쓰는 `remuxMp4` 를 **구간만
  파일 전체로 준 채** 재사용한다 — cts/dts 를 다루는 곳이 두 벌이 되면 한쪽만 고치게 된다.
- **MP4 → WebM 은 전부 재인코딩이다.** WebM 은 H.264 도 AAC 도 담을 수 없다. 화면은 VP9,
  소리는 Opus 로 다시 만들어야 한다. **이 저장소에서 `AudioEncoder` 를 부르는 곳은
  `transcodeToOpus` 하나뿐이다.**

데인 것과 정한 것:

- **오디오를 먼저 끝내고 나서 muxer 를 세운다.** WebM 트랙을 선언하려면 샘플레이트·채널 수를
  미리 알아야 하는데, 그 값의 진짜 출처는 트랙 헤더가 아니라 **디코더가 내놓는 AudioData**
  다(HE-AAC 는 헤더의 두 배로 나온다). 다 돌린 뒤에 세우면 어긋날 자리가 없다.
  Opus 는 분당 1MB 남짓이라 배열에 들고 있어도 감당된다.
- **한쪽 트랙을 통째로 먼저 넣으면 안 된다.** 영상 청크를 넣기 직전에 그보다 이른 오디오를
  흘려 보내야 클러스터가 시간 순서대로 쌓인다.
- **Opus 는 8k~48kHz 를 다 받는다**(실측). 44.1kHz 파일을 위해 리샘플러를 쓸 필요가 없었다.
- **WebM 판정으로 도구 전체를 막지 않는다.** MP4 경로는 코덱을 하나도 부르지 않으므로
  인코더가 없는 기기에서도 멀쩡히 돈다. `canEncodeWebm` 이 false 면 **선택지 하나만** 잠근다.
  비디오와 오디오를 둘 다 물어야 한다 — 한쪽만 되는 기기에서는 반쪽짜리 파일이 나온다.
- **입력은 MP4·MOV·M4V 뿐이다.** mp4box 는 ISOBMFF 만 읽으므로 우리에게 WebM·AVI·MKV 를
  **여는 코드가 없다.** 그래서 "WebM → MP4" 를 목록에 올리지 않는다. 규칙 3.
- QA 는 `clip.mov`(= `clip.mp4` 를 `-c copy` 로 옮겨 담은 짝)로 무손실을 **픽셀로** 증명하고,
  WebM 은 EBML 머리글 `1A 45 DF A3` 과 `decodeAudioData` 로 실제 소리까지 확인한다.

## GA 통계는 우리 QA 가 만든 것이었다 (2026-07-26)

대시보드가 28일 기준 **활성 사용자 282 / 세션 283 / 핵심 이벤트 88** 을 보여 주었다.
사람이 온 것이 아니다. 근거가 넷이다.

1. **Search Console 노출 0 / 클릭 0.** 색인이 열린 지 하루다. 검색에서 올 수가 없다.
2. **사용자 ≈ 세션(282:283).** 사람은 재방문하므로 이 비율이 나오지 않는다.
   Playwright 는 **테스트마다 새 컨텍스트**를 주고, 새 컨텍스트는 새 GA client_id 다 →
   테스트 하나가 사용자 하나가 된다. 프로덕션 스펙 한 번이 방문 100여 건을 만든다.
3. **인기 페이지 상위 5개가 전부 `/ko`.** 6개 언어를 내는 사이트에 한국어만 들어올 수
   없다. 우리 도구 스펙이 전부 `/ko/tools/…` 를 친다.
4. **페이지별 조회수가 스펙의 테스트 수에 비례한다.** pdf-organize 10개·pdf-split 11개…
   그리고 **방금 배포한 video-convert 는 상위에 없다** — 프로덕션 실행이 한 번뿐이다.

그래서 **자동화된 브라우저(`navigator.webdriver`)에는 GA 태그를 심지 않는다.**
`components/Analytics.tsx` 가 그 판단을 갖는다. 분석 자체를 검증하는
`tests/analytics.spec.ts` 만 `__toolsmithAnalyticsOptIn` 으로 명시적으로 켠다 —
켜는 길이 하나뿐이어야 다른 스펙이 실수로 켜지 않는다.

양쪽 방향을 다 고정했다. 한쪽만 지키면 조용히 통계가 죽는다.

- 자동화 → 태그도 요청도 0.
- **실사용자 → 태그가 그대로 나간다.** `navigator.webdriver` 를 false 로 되돌려 확인하되
  요청은 `route.abort()` 로 끊는다 — 이 검사가 진짜 방문을 만들면 그것도 오염이다.

곁들여 고친 것: **앱 라우터의 화면 전환은 새 문서를 부르지 않는다.** 홈에서 링크로 들어간
방문이 통계에 없는 것이 되어 도구별 인기가 실제보다 낮게 잡히고 있었다. 경로가 바뀌면
`page_view` 를 보낸다(첫 화면은 `gtag('config')` 가 이미 보냈으므로 건너뛴다).

**과거 데이터는 지워지지 않는다.** GA4 의 데이터 필터는 소급되지 않으므로 28일 통계는
기준선으로 쓰지 말고, 이 배포(2026-07-26) 이후부터 다시 세는 것이 맞다.

## OCR 은 이 사이트에서 처음으로 "받아야 시작하는" 도구다 (2026-07-26)

지금까지의 도구는 브라우저에 이미 있는 것(WebCodecs·Canvas)이나 수백 KB 짜리 라이브러리로
끝났다. OCR 은 다르다 — **엔진 wasm 3.4MB + 언어 데이터 0.9~2MB** 를 받아야 첫 글자가 나온다.
그래서 규칙 2·5 를 지키는 방식이 이 도구의 설계 그 자체다.

- **`4.0.0_fast` 를 쓴다.** 같은 언어의 `best` 는 5~10배 크다(실측, gzip 전송 크기):

  | 언어 | fast | best |
  |---|---|---|
  | eng | 1.98MB | 10.9MB |
  | jpn | 1.54MB | 16.2MB |
  | kor | 1.11MB | 6.95MB |

  깨끗한 스캔에서는 차이가 작고 흔들린 사진에서는 드러난다. **그걸 확인하자고 16MB 를
  받게 하지 않는다** — 대신 화면과 FAQ 에 이 트레이드를 그대로 적는다.
- **누르기 전에 용량을 말한다.** "엔진과 언어 데이터 약 4.4MB 를 받습니다" 가 버튼 위에
  있고, 언어를 바꾸면 그 숫자도 바뀐다. 스펙이 두 언어의 문구가 서로 다른지를 확인한다 —
  고정 문구를 박아 두면 여기서 걸린다.
- **자산은 전부 남의 CDN 에서 온다**(규칙 5). 엔진·워커는 jsDelivr, 언어 데이터는
  tesseract.js 가 직접 운영하는 tessdata 호스트. Vercel 에서 나가는 것은 0 바이트다.
- **기본 언어는 보고 있는 언어판을 따른다.** `/ko` 면 한국어다. 매번 영어에서 바꾸게 하는
  것은 1MB 를 더 받게 만드는 일이기도 하다.
- **tesseract.js 를 우리 워커 안에서 부르지 않는다.** `createWorker` 가 자기 워커를 띄우므로
  겹친다. PDF 래스터화만 우리 워커가 하고(pdf.js), 인식은 tesseract 가 자기 워커에서 한다 —
  어느 쪽이든 메인 스레드는 막히지 않으므로 규칙 7 은 지켜진다.
- **COOP/COEP 를 켜지 않으므로**(규칙 4) 단일 스레드 코어로 돈다. 느리지만 교차 출처를
  막지 않는다. 이 교환은 다시 논의하지 않는다.

QA 에서 확인한 것:

- 픽스처에 **숫자를 섞었다**(`TEST 12345`). 낱말만 맞히면 사전 보정으로도 그럴듯해지지만
  숫자는 사전이 도와줄 수 없다 — 그림을 정말 읽었을 때만 나온다.
- `scan.pdf` 는 **그림만 박힌 A4 한 장**이라 진짜 글자가 없다. 결과가 나왔다면 래스터화
  경로가 실제로 돈 것이다.
- **기본 언어로 라틴 문자를 읽으면 뭉갠다**(한국어 모델로 `TOOLSMITH` → `1001Ｌ5041150`,
  숫자 `12345` 는 맞힘). 결함이 아니라 이 도구가 언어 선택을 맨 앞에 내놓는 이유다.
  스펙은 픽스처에 맞는 언어를 골라서 읽는다.

## pdf.js 를 워커에서 쓰면 CJK 가 빈 네모로 그려진다 (2026-07-26, 실물 문서로 발견)

**증상.** 한국어 슬라이드 PDF 를 OCR 에 넣으니 `다다다 다다 ㅁ다다 ㅁㅁㅁ…`, 일본어 보고서는
`皿是HHHHHHHH…` 가 나왔다. 확신도 47% / 46%.

**원인은 OCR 이 아니라 그림이었다.** pdf-organize 썸네일로 같은 파일을 열어 보니 페이지가
통째로 `□□□` 였다. pdf.js 는 PDF 에 박힌 글꼴을 `document.fonts` 에 @font-face 로 설치한 뒤
캔버스에 그리는데, **워커에는 document 가 없다.** 설치에 실패하면 대체 글꼴로 그리고,
그 글꼴에 한글·한자가 없으니 빈 네모가 된다. **예외도 경고도 없다** — 그림만 틀린다.
OCR 은 그 네모를 충실히 읽어 낸 것뿐이다.

**틀린 가설을 하나 거쳤다.** 처음엔 cmap 이 없어서라고 보고 `cMapUrl` 을 붙였는데 결과가
한 글자도 바뀌지 않았다. PDF 안을 열어 보니 글꼴이 **탑재돼 있고**(FontFile2 ×7) 인코딩이
`Identity-H` 라 cmap 이 애초에 필요 없는 파일이었다. 화면을 눈으로 본 뒤에야 방향이 잡혔다.

**해결:** `disableFontFace: true`. pdf.js 가 글리프를 **경로로 직접 그려** 글꼴 설치가 필요
없어진다. `lib/pdf/pdfjs-options.ts` 가 그 설정을 갖는다.

| 실물 문서 | 고치기 전 | 고친 뒤 |
|---|---|---|
| 한국어 슬라이드 (CC BY 4.0) | 확신도 47%, 전부 `ㅁ` | 확신도 **82%**, 문자 회수율 **91.7%** |
| 일본어 보고서 (CC BY-SA 4.0) | 확신도 46%, 전부 `H` | 확신도 **91%**, 문자 회수율 **95.5%** |

편집거리 기준 정확도는 한국어 59.7% / 일본어 77.3% 로 더 낮게 나오는데, 슬라이드는
**읽는 순서**가 텍스트 레이어와 다르고 일본어는 전각/반각 문장부호가 갈리기 때문이다.
문장 자체는 정확히 읽혔다 — "첫번째 걸음 - 어떤 기준으로 인물을 등재할 것인가?" 는 완벽했다.
**결론: `4.0.0_fast` 는 깨끗한 문서에 충분하다.** `best` 모델은 당분간 필요 없다.

**이 결함이 오래 살아 있었던 이유가 중요하다.** 우리 PDF 픽스처는 전부 표준 14종 라틴
글꼴만 쓴다. 그 글꼴들은 대체 글꼴에도 글리프가 있어서 **아무 테스트도 깨지지 않았다.**
pdf-organize 썸네일도 같은 병을 앓고 있었다(2026-07-24 배포 이후 줄곧).
`tests/pdf-fonts.spec.ts` 가 플래그가 사라지는 것을 막지만, 진짜 확인은 실물 문서로 한다.

## DuckDB-wasm 은 35MB 인데 왜 규칙 6 에 안 걸리나 (2026-07-26)

ffmpeg.wasm 은 30.7MB 라서 뺀 것이 아니라 **GPL 이라서** 뺐다. 30MB 를 브라우저로 보내는
것은 배포이고, 그러면 사이트 전체가 GPL 이 된다. **DuckDB-wasm 은 MIT 다.** 크기는
비슷하지만(비압축 35.6MB) 같은 이유로 거절할 근거가 없다.

실제로 오가는 양은 다르다 — **브로틀리 전송 6.2MB**(워커 186KB 포함 6.4MB). OCR 의 4.4MB
와 같은 자릿수다. 그래서 OCR 과 **같은 약속**을 건다: 누르기 전에 용량을 말하고, 누른
뒤에만 받고, 받는 곳은 jsDelivr 다.

지킨 것과 그 방법:

- **`coi` 번들을 후보에서 뺐다.** `selectBundle` 은 준 것 중에서만 고르므로, 목록에 없으면
  SharedArrayBuffer 경로로 갈 방법이 없다. 규칙 4 를 코드로 못 박은 자리다.
  스펙이 받은 URL 에 `coi` 가 없는지 확인한다.
- **교차 출처 스크립트로는 Worker 를 만들 수 없다.** `importScripts("<cdn>")` 한 줄짜리
  Blob 으로 감싸는 것이 duckdb-wasm 이 문서에 적어 둔 방법이다.
- **파일을 읽어 올리지 않는다.** `registerFileHandle` 로 File 핸들만 넘기면 DuckDB 가
  필요한 조각만 읽는다. 넓은 Parquet 에서 두 열만 보는 질의는 거의 아무것도 읽지 않는다.
- **Arrow 는 정수를 BigInt 로 준다.** 그대로 React 에 넘기면 렌더가 던진다. `cell()` 이
  BigInt·Date·객체를 전부 문자열로 눕힌다. 스펙이 `id` 열이 `"1"` 로 나오는지 본다.
- **SQL 오류는 DuckDB 의 문장을 그대로 보여 준다.** 우리가 요약하면 어디가 틀렸는지 못 찾는다.

QA 에서 확인한 것:

- 집계 결과를 **손으로 검산한 값과 대조한다**(Seoul 3건 3600, Busan 2건 900, Daegu 1건 50.75).
  "쿼리가 돌았다" 는 아무것도 증명하지 않는다.
- **Parquet 픽스처는 DuckDB 자신이 만들었다.** Node 에 Parquet 을 쓰는 도구가 없어
  의존성을 늘리는 대신 브라우저에서 `COPY t TO 'out.parquet'` 한 결과를 저장했다.
  CSV 와 Parquet 의 합계가 같은지를 보므로 왕복이 함께 검증된다.
- 열마다 타입을 다르게 둔 픽스처로 **타입 추론**을 본다. 숫자 열이 문자열로 잡히면
  `SUM` 이 안 되는데, 표만 보고는 알 수 없다.

## 이미지 압축은 왜 별도 페이지인가 (2026-07-26)

`image-convert` 안에 품질 슬라이더가 이미 있다. 그런데도 따로 낸 이유는 **검색 의도가
다르기** 때문이다 — "이미지 용량 줄이기" 로 오는 사람은 형식을 바꾸고 싶지 않다.
그래서 두 도구의 기본값이 반대다.

| | image-convert | image-compress |
|---|---|---|
| 기본 출력 | WebP(가장 작다) | **원본 형식 유지** |
| 화면이 앞세우는 것 | 형식 선택 | **절감량 합계** |
| 기본 품질 | 0.82 | 0.75 |

**PNG 를 정직하게 다루는 것이 이 도구의 핵심이다.** PNG 는 무손실이라 품질을 내려도
1바이트도 줄지 않는다. 아무 말도 없으면 사용자는 도구가 고장났다고 생각한다. 그래서
PNG 가 들어온 **순간**(누르기 전에) 왜 안 줄어드는지와 무엇을 하면 되는지를 말한다 —
크기를 줄이거나 WebP 로 바꾸거나. 스펙이 그 문구가 PNG 에만 나오는지 확인한다.

`sourceFormat()` 은 읽을 수는 있지만 **쓸 수 없는** 형식(HEIC·GIF·BMP)에 `null` 을 준다.
그럴 때만 JPG 로 떨어뜨린다 — 규칙 3 을 지키려면 "형식 유지" 가 지킬 수 없는 약속이
되는 자리를 코드가 알아야 한다.

## 크롭은 드래그가 아니라 비율로 간다 (2026-07-26)

드래그로 영역을 고르는 UI 를 만들지 않았다. 실제 수요의 대부분("인스타 정사각형",
"세로 게시물 4:5")은 **가운데 기준 비율 자르기**로 덮이고, 드래그는 코드가 몇 배인데
모바일 터치까지 제대로 하려면 더 커진다. **예측 가능한 일 하나를 제대로 하는 쪽**을
골랐고, FAQ 에 "어느 부분을 남길지 직접 고르려면 편집 프로그램이 맞다" 고 적었다.
수요가 보이면 그때 붙인다.

- **`planResize()` 가 계산의 유일한 자리다.** 화면은 누르기 전에 "1600×1200 → 540×675"
  라고 말해야 하고 워커는 실제로 그 크기를 만들어야 하는데, 두 곳에서 따로 계산하면
  언젠가 어긋난다. GIF 의 `gif-timing` 과 같은 이유다. 스펙이 **화면 문구와 디코드한
  파일 크기가 같은지**를 직접 대조한다.
- **늘리지 않는다.** 원본보다 큰 너비를 요청하면 원본 크기로 내고 그렇다고 말한다.
  없는 화소를 지어내면 흐려지기만 하는데 화면의 숫자는 커져서 좋아진 것처럼 보인다 —
  규칙 3 이 금지하는 바로 그 종류의 거짓말이다.
- `convertToBlob` 이 못 만드는 형식에 조용히 PNG 를 뱉는 문제는 여기서도 같다.
  반환된 `blob.type` 을 대조해 다르면 던진다.
- 계산 검증 2건은 **브라우저 없이** 돈다(`planResize` 직접 호출). 자르기 규칙이 바뀌면
  UI 를 띄우지 않고도 걸린다.

## Tier 2 의 첫 도구 — 배경 제거 (2026-07-26)

AI 도구의 첫 칸이다. Tier 1 과 달라지는 것은 **모델을 받아야 시작한다**는 것 하나뿐이고,
규칙은 그대로다. 걸린 곳이 두 군데였는데 둘 다 라이선스와 배포 경로였다.

**1. 가중치에 걸린 라이선스는 코드 라이선스와 별개다.** "배경 제거 브라우저" 로 검색하면
`briaai/RMBG-1.4` 가 제일 먼저 나오고 품질도 이 바닥 최고 수준이다. 그런데 모델 카드가
직접 비상업 라이선스라고 적는다. MODNet 은 CC BY-NC-SA, `@imgly/background-removal` 은
AGPL. **ffmpeg.wasm 때와 똑같은 함정이고, 똑같이 걸러야 한다.** 채택한 것은 앨버타대학의
**U²-Net(Apache-2.0)** 이다. 쓰는 ONNX 는 rembg 가 재배포한 공식 체크포인트를 HF 에 다시
올린 `Heliosoph/u2net-onnx` 이고, 저장소가 `base_model: xuebinqin/U-2-Net` 로 출처를 밝힌다.
`tests/remove-bg.spec.ts` 의 **브라우저 없이 도는 검사**가 모델 주소를 못 박는다 —
언젠가 "품질이 더 좋다" 는 이유로 슬쩍 갈아 끼우는 일을 막기 위해서다.

**2. `onnxruntime-web` 을 npm 의존성으로 두면 규칙 5 가 깨진다.** 이 패키지의 기본
export(`import "onnxruntime-web"`)는 `*.bundle.min.mjs` 인데, **wasm 을 base64 로 품고 있다.**
import 하는 순간 20MB 가 우리 번들에 들어와 Vercel 에서 나간다. 외부 wasm 을 쓰는 변형이
있지만 그것을 고르려면 번들러의 export condition 을 건드려야 한다. 그래서 **의존성에서
아예 뺐다** — jsDelivr 의 `ort.webgpu.min.js` 를 실행 시점에 받고, 타입은 tesseract 때처럼
쓰는 만큼만 좁혀 적는다. 규칙을 문서가 아니라 **구조**가 지키게 한 것이다.

- **워커가 모듈 워커다**(`{ type: "module" }`). 고전 워커에서는 `import()` 를 쓸 수 없는데,
  엔진을 CDN 에서 실행 시점에 받으려면 그것이 필요하다. type 을 빼면 엔진 로딩이 통째로
  실패한다. 이 저장소에서 모듈 워커는 여기가 처음이다.
- **`numThreads = 1` 을 명시한다.** COOP/COEP 를 켜지 않으므로(규칙 4) `SharedArrayBuffer`
  가 없다. 적지 않으면 ORT 가 스레드를 띄우려다 실패한다.
- **모델 두 개를 내놓고 무엇이 다른지 미리 말한다.** `u2netp` 4.4MB / `u2net` 168MB.
  40배 차이인데 결과도 눈에 띄게 다르다 — 작은 쪽은 배경의 유령이 남고, 큰 쪽은 인물과
  소품만 깨끗이 떨어진다(1896년 공개 사진으로 실측). 그래서 "윤곽이 거침 / 머리카락까지"
  라고 선택지에 그대로 적었다.
- **모델은 320×320 으로 본다.** 마스크도 320×320 으로 나오므로 원본 크기로 다시 늘려야
  하고, 4000px 사진이면 그 늘림이 윤곽선에 보인다. FAQ 에 적었다 — 손으로 딴 마스크가
  아니라는 것을 알고 쓰게 해야 한다.
- **`needs` 를 `"all"` 로 뒀다.** WebGPU 가 있으면 그리로 가고 없으면 wasm 으로 내려가
  **끝까지 돈다**(느릴 뿐이다). 할 수 있는 것을 못 한다고 적는 것도 규칙 3 위반이다.
  어느 쪽으로 돌았는지는 결과 옆에 그대로 쓴다. 실측: 헤드리스 Chromium 은 WebGPU 가
  없어 CPU 로 떨어지는데, 960×1210 사진이 작은 모델 5.3초 / 정밀 모델 11.3초였다
  (모델 내려받는 시간 포함).
- 픽스처는 **밝은 배경 한가운데 어두운 덩어리**다(`subject.png`). U²-Net 은 눈에 띄는
  것을 찾는 모델이므로 픽스처도 그래야 하고, 모서리·가운데의 알파를 읽으면 마스크가
  물체 위에 앉았는지 손으로 검산된다. 실제 사진에서의 품질은 스펙이 아니라 사람이 본다.

## 업스케일은 "가장 선명한 모델" 이 아니라 "CPU 에서 도는 모델" 로 갔다 (2026-07-26)

배경 제거 다음 칸이다. 여기서 배운 것은 **모델을 라이선스만 보고 고르면 안 된다**는 것이다.

**~~테스트 브라우저에 WebGPU 가 없다~~ — 이 문장은 틀렸다. 2026-07-26 정정.**
당시 `about:blank` 에서 `navigator.gpu` 를 물어 "없음" 이 나왔는데, **보안 컨텍스트가
아니어서** 그랬다. 실제 페이지에서 다시 재니 어댑터가 잡힌다(`vendor=nvidia
arch=lovelace`). 없는 것은 Playwright 가 **기본으로 쓰는 헤드리스 셸 빌드**뿐이고,
`channel: "chromium"` 은 헤드리스에서도 어댑터를 준다. 자세한 것은 아래
"WebGPU 는 테스트할 수 있다" 절.

그래도 이 모델 선택은 그대로 옳다. **이유가 바뀌었을 뿐이다** — "검증할 수 없어서" 가
아니라 **"WebGPU 가 3배 빠른 것으로는 Swin2SR 을 구제하지 못해서"** 다. 실측으로
Swin2SR 은 GPU 에서도 512×512 사진에 50초가 걸린다.

| 후보 | 라이선스 | 크기 | CPU 실측 | 판정 |
|---|---|---|---|---|
| Swin2SR ×4 (`caidas/…-bsrgan-psnr`) | Apache-2.0 | 21MB(양자화) | **128×128 에 9.7초**, 세션 열기 10.2초 | 탈락 |
| **realesr-general-x4v3** | **BSD-3-Clause** | **4.87MB** | **512×512 에 16.5초**, 세션 열기 0.34초 | **채택** |

WebGPU 는 약 3배 빠르다(아래 절 실측). Swin2SR 을 GPU 로 돌려도 512×512 에 50초대라
**그래픽카드가 있는 사람에게도 느리다.** 반대로 realesr 는 GPU 에서 4.8초다.

화소당으로 환산하면 **60배 차이**다. Swin2SR 은 트랜스포머고 이쪽은 SRVGGNetCompact 라
층이 얕다. 선명도는 Swin2SR 이 낫지만, 그 선명함은 그래픽카드가 있는 사람만 볼 수 있다.

- **조각내기.** 알맹이 384 에 사방 32 를 덧대 넣고 결과에서 알맹이만 오려 붙인다.
  완전 합성곱이라 값이 틀어지는 곳은 가장자리뿐이므로, 덧댄 만큼 버리면 **이음매가
  생기지 않는다** — 흐리게 섞어 가릴 필요가 없다. 덧대는 폭은 수용영역(3×3 × 16층 ≈ 33px)
  보다 커야 한다. `planTiles()` 를 브라우저 없이 검사한다(알맹이가 겹치지 않고 정확히
  원본을 덮는가).
- **원본 100만 화소 상한.** ×4 는 화소가 16배다. 넘으면 버튼을 비활성화하고 이유를 적는다 —
  탭을 몇 분 얼려 놓고 아무것도 못 내는 것이 가장 나쁜 결과다.
- **누르기 전에 어느 실행기로 갈지 말한다.** `hasWebGPU()` 는 아무것도 받지 않고 답하므로,
  없으면 실측 처리속도로 예상 초까지 계산해 미리 경고한다. 규칙 4 의 "조용한 실패 금지" 는
  실패뿐 아니라 **조용한 성능 절벽**에도 해당한다.
- **×2 는 ×4 를 절반으로 줄여 만든다.** 바로 ×2 로 키우는 것보다 낫다 — 모델이 지어낸
  세부가 축소되면서 정돈된다. 시간은 ×4 와 같다(앞의 계산이 같다).

### 실측이 카피를 고쳤다

1896년 공개 사진을 240px 로 줄였다가 ×4 로 되키워 단순 확대(lanczos3)와 비교했더니
**모델 쪽이 더 나빴다.** 격자무늬 옷감의 결이 통째로 지워지고 얼굴이 밀랍처럼 됐다.

이 모델은 **손상 복구용**이라 잡음이라고 읽은 것을 지우는데, 필름 그레인과 옷감의 고운
결도 잡음으로 읽힌다. 같은 사진을 품질 35 JPEG 로 저장해(웹에서 흔한 상태) 다시 재니
이번엔 **모델이 확실히 이겼다** — 블로킹이 사라지고 윤곽이 돌아왔다.

그래서 FAQ 에 "결과가 밀랍처럼 매끈해졌어요" 항목을 6개 언어에 넣고 **양쪽 실측을 그대로
적었다.** 이기는 쪽만 적었으면 규칙 3 위반이다. 실제 자료로 확인하지 않았으면
"세부를 되살립니다" 라고만 적고 넘어갔을 것이다.

## 컷아웃은 인코더를 한 번, 디코더를 클릭마다 (2026-07-26)

배경 제거(#17)와 하는 일이 비슷해 보이지만 성격이 반대다. **저쪽은 모델이 고르고
이쪽은 사용자가 가리킨다.** 사진에 물건이 여럿일 때, 혹은 주인공이 아닌 것을 떼고 싶을 때
쓴다. 두 도구를 다 두는 이유가 그것이다 — 피사체가 하나로 분명하면 클릭이 필요 없는
배경 제거가 낫고, 그렇지 않으면 이쪽이다.

**SAM 이 두 조각인 것이 이 UI 를 가능하게 한다.** 그림을 한 번 훑어 임베딩을 만드는
무거운 인코더와, 그 임베딩에 클릭 좌표를 얹는 가벼운 디코더로 나뉘어 있다.
실측(CPU wasm 단일 스레드): **인코더 6.0초, 디코더 0.10초.** 그림을 바꿀 때만 6초를 내고
클릭은 즉시 응답한다. 그래서 워커가 임베딩을 들고 있고, 버튼이 "준비하기" 다.

모델은 **SlimSAM-77**(Apache-2.0). 원본 SAM ViT-B 도 Apache-2.0 이지만 인코더가
**359MB** 다 — 압축본은 **8.9MB**(양자화)로 15배 작다. 업스케일 때와 같은 판단이다:
가장 좋은 모델이 아니라 **실제로 기다릴 수 있는 모델**을 고른다.

- **클릭 라벨은 int64 다.** float32 로 주면 `Unexpected input data type` 으로 거절당한다.
  `lib/onnx/runtime.ts` 에 `OrtIntTensor` 를 더한 이유가 이것뿐이다.
- **좌표는 1024 상자 기준으로 옮겨서 준다.** 긴 변을 1024 에 맞춰 줄이고 오른쪽·아래를
  0 으로 채우므로, 마스크도 같은 상자로 나오고 왼쪽 위만 잘라 쓰면 된다. `planSegment()`
  를 브라우저 없이 검사한다 — 클릭이 엉뚱한 곳으로 가는 것을 여기서 막는다.
- **후보가 셋이다**(부분 / 부분+ / 전체). 어느 것이 맞는지는 모델도 모르므로 함께 나오는
  iou 점수가 가장 높은 것을 쓴다.
- **미리보기는 256 마스크를 늘려 그린다.** 클릭마다 원본 크기 마스크를 만들면 0.1초짜리
  응답이 사라진다. 원본 크기는 내려받기를 누를 때만 만든다.

### 실측으로 확인한 것

1896년 공개 사진(960×1210)에서 **주인공이 아닌 항아리**를 눌렀다.
- 점 1개: 항아리 **몸통만** 나왔다(손잡이·주둥이 빠짐) — 모델이 "부분" 후보를 골랐다.
- 점 2개: 주둥이와 손잡이까지 **항아리 전체**가 나왔다.

즉 FAQ 에 적은 "점을 하나 더 찍으면 정리된다" 는 실제로 그렇다. 두 번째 점을 손잡이가
아니라 그 옆 어두운 배경에 찍었더니 그 배경이 함께 딸려 왔는데, **'빼기' 가 왜 필요한지**를
그대로 보여 준다.

## WebGPU 는 테스트할 수 있다 (2026-07-26, 앞선 기재 정정)

한동안 "테스트 브라우저에 WebGPU 가 없다" 고 적어 두고 그것을 전제로 모델을 골랐다.
**그 전제가 틀렸다.** `about:blank` 에서 물었기 때문이고, 보안 컨텍스트가 아니면
`navigator.gpu` 가 노출되지 않는다. 실제 페이지에서 다시 재면 이렇게 나온다.

| 조합 | `requestAdapter()` |
|---|---|
| 기본(헤드리스 셸) | **null** |
| 기본 + 헤드풀 | 어댑터 있음 |
| `channel: "chromium"` 헤드리스·헤드풀 | 어댑터 있음 |
| `channel: "chrome"` 헤드리스·헤드풀 | 어댑터 있음 |

즉 어댑터가 없는 것은 Playwright 가 기본으로 쓰는 **헤드리스 셸** 빌드뿐이다.
`playwright.config.ts` 에 **`chromium-webgpu` 프로젝트**를 더해 모델 도구 셋을 그 길로도
친다. 거기서는 스펙이 "GPU 로 처리" 를 **정확히** 요구한다 — 어댑터가 사라졌을 때
조용히 CPU 로 통과하면 검증이 아니기 때문이다.

### 속도 (RTX 40 노트북, 첫 실행)

| | CPU(wasm 단일 스레드) | WebGPU | 배수 |
|---|---|---|---|
| 업스케일 512×512 | 16.5초 | **4.8초** | 3.4× |
| 업스케일 256×256 | 4.1초 | **1.2초** | 3.4× |
| SAM 인코더 1024×1024 | 6.0초 | **2.3초** | 2.6× |

20~50배를 기대했다면 그렇지 않다. ORT 의 WebGPU EP 는 셰이더 컴파일과 전송 오버헤드가
있고, 첫 실행에는 그것이 다 들어간다. **3배는 의미가 있지만 판을 뒤집지는 않는다** —
CPU 에서 못 쓸 모델은 GPU 로도 대개 못 쓴다.

### 붙이자마자 실제 결함이 나왔다

컷아웃이 WebGPU 에서 **응답을 영영 안 했다.** 클릭이 부른 디코더 실행이 아직 도는 중에
"오려 내기" 가 같은 세션에 두 번째 `run()` 을 걸기 때문이다. wasm 은 단일 스레드라
우연히 줄을 서서 여태 드러나지 않았다. `lib/segment/segment-core.ts` 의 `serialize()` 로
모델 호출을 한 줄에 세워 고쳤다 — **빠르게 누르는 실제 사용자가 겪었을 결함**이다.

이것이 이 프로젝트를 더한 이유 그 자체다. 폴백 경로만 검증하면, 정작 대부분의 사용자가
타는 길은 아무도 안 본 채로 나간다.

## 자막은 fp32 밖에 못 쓴다 (2026-07-26)

Tier 2 에서 가장 무거운 도구다. 고르기 전에 잰 것을 그대로 남긴다.

**모델.** Whisper 는 **Apache-2.0** 이고 99개 언어를 한다. Moonshine 은 MIT 이지만
**영어 전용**이라 6개 언어 사이트에는 맞지 않는다 → 탈락.

**정밀도를 낮춘 모델이 실제로 동작하지 않는다.** 이것이 받을 양을 정했다.

| | wasm | WebGPU |
|---|---|---|
| q8(양자화) | 세션이 안 열림 | 세션이 안 열림 |
| fp16 | 세션이 안 열림 | tiny 는 문장이 흐트러지고 **base 는 완전히 깨짐** |
| **fp32** | ✓ | ✓ |

q8 오류는 `MatMulNBits ... Missing required scale`. fp16 base 는 세션은 열리는데
`"We are. We are. We are…"` 만 뱉는다 — **조용히 망가지는 쪽이라 더 위험하다.**
그래서 tiny 151MB / base 291MB 를 그대로 보내고 용량을 미리 말한다.

**속도** (16초 음성, RTX 40 노트북):

| | 로드 | 인식 |
|---|---|---|
| tiny WebGPU | 3.6초 | 1.6초 |
| tiny wasm | 4.3초 | 1.5초(11초 음성) |
| base WebGPU | **18~23초**(셰이더 컴파일) | 1.8초 |

실시간의 0.1~0.14배라 5분 영상이면 1분 안쪽이다. **CPU 로도 쓸 만하다.**

### 한국어 판정이 표본 하나에 뒤집힐 뻔했다

1948년 김구 연설 녹음(퍼블릭 도메인)으로 먼저 쟀더니 tiny 는 `"아, 아, 아…"` 만,
base 도 몇 마디 뒤 같은 반복에 빠졌다. 여기서 멈췄으면 **"tiny 는 한국어를 못 한다"** 고
적었을 것이다.

깨끗한 현대 한국어 16초로 다시 재니 tiny 는 40여 단어 중 **2건**, base 는 **1건** 틀렸다.
**녹음 품질 문제이지 언어 문제가 아니었다.** 대신 진짜 실패 모드를 하나 얻었고 —
잡음이 심하면 같은 말을 반복하며 무너진다 — 그것을 FAQ 가 아니라 **화면 상시 경고**로
띄웠다. 가장 자주 만날 실패라 FAQ 에만 두면 늦는다.

### 모델이 커지자 앞선 도구의 패턴이 깨졌다

`["webgpu", "wasm"]` 순서로 열어 보는 방식을 배경 제거·업스케일·컷아웃에서 그대로
가져왔는데 여기서는 못 쓴다. **transformers.js 는 실패를 판정하기 전에 모델을 다 받는다** —
어댑터가 없는 브라우저에서 151MB 를 받고 실패한 뒤 wasm 으로 또 받는다. 실측에서
테스트 하나가 **9분**을 넘겼다. `hasWebGPU()` 로 먼저 묻고 한 번만 열도록 고치니
**18초**가 됐다. 모델이 5~19MB 일 때 무해했던 패턴이 10배가 되자 못 쓸 물건이 된 것이다.

- 소리는 **WebCodecs 로** 꺼낸다. 워커에는 `decodeAudioData` 가 없다(창 전용 API).
  WAV 만 헤더가 단순해 직접 읽는다.
- 받는 형식은 **MP4 · MOV · M4A · WAV**. MP3 는 뺐다 — 읽으려면 디코더를 더 받아야 한다.
  **할 수 있는 척하느니 목록에서 빼는 쪽**이다.
- 16kHz 로 내릴 때 **창 안을 평균 낸다.** 건너뛰며 뽑으면 고음이 접혀 지직거린다.
- 스펙이 **fp16·q8 로 되돌아가는 것을 막는다.** "용량을 줄이자" 는 다음 사람이 조용히
  망가지는 쪽으로 가지 않도록.

## 자막 번역 — 하마터면 라이브러리 버전 때문에 접을 뻔했다 (2026-07-26)

#16 은 **후보 다섯을 전부 재 보고** 하나만 남았다. 순서는 라이선스 → 크기 → 속도 →
품질이었고, 셋이 라이선스와 크기에서 떨어졌다(위 "채택하지 않기로 한 것" 참고).

### 실측표

| 후보 | 라이선스 | 최소 실행 크기 | 결과 |
|---|---|---|---|
| TranslateGemma 4B | Gemma 약관 + 수동 승인 게이트 | 2.7GB (q4f16) | 탈락 — 라이선스 |
| NLLB-200 600M | CC-BY-NC-4.0 | — | 탈락 — 비상업 |
| opus-mt `en-mul` | Apache-2.0 | 112MB | 탈락 — 한국어가 줄루어로 나옴 |
| opus-mt 단일쌍 | Apache-2.0 | 446MB / **한 방향** | 잘 되지만 **en→ko ONNX 판이 없다** |
| **m2m100 418M** | **MIT** | **632MB** | **채택** — 100개 언어, 어느 방향이든 |

### 가장 위험했던 함정은 모델이 아니라 **라이브러리 버전**이었다

transformers.js **4.2.0 에서는 q8 seq2seq 가 세션 생성부터 실패한다**
(`qdq_actions.cc: TransposeDQWeightsForMatMulNBits Missing required scale`).
m2m100 도 opus-mt 도 똑같이 죽었기 때문에 **"이 계열은 브라우저에서 안 된다" 로
결론 낼 뻔했다.** 실제로는 같은 파일이 **3.7.6 에서 3초에 열리고 제대로 번역한다.**

되짚어 보면 자막 생성 때 "q8 은 열리지 않는다" 고 적은 것도 **4.2.0 에서의 관찰**이다.
모델 탓으로 적었지만 런타임 탓이었을 수 있다. 자막은 fp32 로 잘 돌고 있어 굳이 흔들지
않지만, **"모델이 안 된다" 는 판정은 런타임 버전과 짝지어 적어야 한다**는 것을 배웠다.

그래서 `lib/translate/translate-core.ts` 는 **3.7.6 에 고정**되어 있고 스펙이 그 문자열을
못 박는다. 자막 생성이 4.2.0 을 쓰고 있으니 **"버전을 통일하자" 는 손은 언젠가 반드시
온다** — 그때 조용히 죽는 대신 테스트가 빨갛게 된다.

### WebGPU 로는 못 간다

3.7.6 에서는 세션이 아예 열리지 않고(오류 코드만 나온다), 4.2.0 에서는 열리되 같은 낱말만
반복하며 무너진다("This This This…", "Beg Beg Beg…"). **CPU 로만 간다.** 그래서 이 도구는
`lib/tools.ts` 에서 `needs: "all"` 이다 — WebGPU 를 요구한다고 적으면 거짓말이 된다.

### 묶어서 넘기면 느려진다

20줄 기준 **낱개 30.2초 vs 묶음 49.1초.** 한 줄씩 부르는 것은 게을러서가 아니다.
줄당 1.5초는 20줄 내내 흔들리지 않았다(1.41 … 1.53). 그래서 남은 시간을 미리 말할 수 있다.

### 품질은 정직하게 적었다

평범한 문장은 잘 하고 **관용구에서 미끄러진다** — "let's wrap this up" 이 스페인어·독일어
양쪽에서 "이제 시작하자" 쪽으로 나왔다. 20줄 중 15줄이 좋고 5줄이 어색하지만 뜻은 통했다.
418M 모델의 정직한 수준이고, **화면에 항상 보이는 경고로 적는다**(FAQ 에 묻지 않는다).

## 기술 함정 (걸려본 것 / 걸릴 것)

- `COEP: require-corp`를 켜면 **교차 출처 리소스가 전부 차단**된다 → HF CDN 모델 로드와 정면 충돌.
  `credentialless`를 쓰거나 COEP가 필요한 경로에만 헤더를 건다.
  **실측(2026-07-25)**: v1 은 COOP/COEP 를 걸지 않았고 `crossOriginIsolated === false` 인 상태로
  이미지 도구가 정상 동작한다. ffmpeg.wasm 을 붙이는 시점에 `/tools/video/*` 로 스코프해서 켠다.
- Vercel CLI 첫 배포는 git 연결이 없으면 **preview 가 아니라 production 으로 올라간다.**
  `--target preview` 를 명시해야 한다.
- 워커에서 `Omit<Union, "id">` 는 공통 키만 남겨 payload 를 날린다. 조건부 타입으로 분배해야 한다.
- **지연 로딩은 dev 서버에서 판정하지 말 것.** Turbopack dev 는 동적 import 청크를 미리
  당겨온다 → dev 만 보면 멀쩡한 코드가 규칙 2번 위반처럼 보인다.
  **실측(2026-07-25, 프로덕션)**:
  - `/tools/image-convert` 로드 546KB → HEIC 를 넣은 순간 **+1.48MB**(libheif). 정상.
  - `/tools/pdf-merge` 로드 529KB → PDF 를 넣은 순간 **+461KB**(워커+pdf-lib). 정상.
  - `/tools/video-to-gif` 로드 530KB → 영상을 넣은 순간 **+204KB**(mp4box+gifenc). 정상.

  같은 페이지를 dev 에서 보면 둘 다 로드 시점에 이미 내려와 있다. **판정은 반드시
  `BASE_URL=<배포주소> pnpm test` 로 한다.** 두 스펙 모두 프로덕션 전용 검사를 갖고 있고,
  dev 에서는 자동으로 스킵된다.
- pdf-lib 파서는 관대해서 PDF 가 아닌 바이트도 `PDFDocument.load` 는 통과시키고
  `getPageCount()` 에서 TypeError 로 터진다. load 만 try 로 감싸면 오류 분류가 새어 나간다.
- pdf-lib 은 암호화를 **복호화하지 않는다.** `ignoreEncryption: true` 로 열면 내용이 깨진
  결과가 조용히 나온다 → 암호 PDF 는 열지 말고 거부해야 한다.
- **pdf-lib 과 pdf.js 는 같은 사정을 다른 말로 알린다.** pdf-lib 은 `EncryptedPDFError`,
  pdf.js 는 `PasswordException`("No password given" — 'encrypted' 라는 말이 없다).
  pdf.js 에게 먼저 물으면 암호 걸린 파일에 "읽을 수 없습니다" 라고 잘못 안내하게 된다 →
  **썸네일을 그리기 전에 pdf-lib 으로 먼저 연다.** 덤으로 못 그릴 파일에 pdf.js(1.5MB)를
  내려받지 않는다.
- pdf.js 6 에는 `PDFDocumentProxy.destroy` 가 없다. `getDocument()` 가 준 **로딩 태스크**를
  destroy 해야 pdf.js 가 띄운 워커까지 정리된다.
- **회전은 원본 값에 더한다.** 스캔본은 `/Rotate 90` 을 달고 있는 일이 흔하고, 사용자가 화면에서
  본 것은 그 회전이 적용된 모습이다. 덮어쓰면 눈에 보이던 것과 다른 결과가 나온다.
- **PDF 압축은 페이지를 굽지 않는다.** 페이지를 통째로 래스터화하면 훨씬 많이 줄지만 글자가
  글자이기를 그만둔다(선택·검색·화면낭독기 전멸). 안에 박힌 **JPEG(DCTDecode)만** 다시
  인코딩한다. Flate 이미지는 색공간·비트깊이 조합이 너무 다양해 건드리지 않고,
  `Decode` 배열(색 반전 등)이 있으면 건너뛴다. `SMask`/`Mask` 가 있으면 크기를 바꾸지
  않는다 — 마스크와 픽셀 수가 어긋나면 문서가 깨진다.
- **다시 저장하는 것만으로도 몇 % 줄어든다.** 그 몫을 절감률로 표시하면 하지 않은 일을 한
  것처럼 보인다 → 실제로 사진을 갈아 끼웠을 때(`rewritten > 0`)만 `-N%` 를 붙인다.
  이건 테스트가 잡아낸 실제 결함이다.
- **dev 서버가 떠 있는 동안 `pnpm build` 를 돌리지 말 것.** 둘이 같은 `.next` 를 쓰기 때문에
  실행 중인 dev 서버의 캐시가 깨지고, 그때부터 테스트가 `SyntaxError: Unexpected end of
  JSON input` 과 함께 무더기로 무너진다. 겪고 나면 원인을 찾기 어렵다.
- **Playwright 워커 수도 같은 증상을 만든다(2026-07-26).** 기본값(코어의 절반, 이 기계는 12)
  으로 돌리면 `next dev` 한 대에 12개가 동시에 컴파일을 요구하다가 `.next` 매니페스트를
  쓰는 중에 읽어 버린다 → 전 페이지가 `SyntaxError: Unexpected non-whitespace character
  after JSON` 으로 죽고 85개 중 1개만 통과한다. **`.next` 를 지워도 낫지 않는다** — 부하
  문제이지 캐시 문제가 아니기 때문. `playwright.config.ts` 에 `workers: 4` 로 고정했다
  (그러자 42초에 전부 통과). 배포본(정적)을 칠 때는 제한하지 않는다.
- Next.js 가 상위 디렉터리 lockfile 때문에 워크스페이스 루트를 잘못 잡는다 →
  `next.config.ts` 의 `turbopack.root` 로 고정.
- ffmpeg.wasm 멀티스레드와 `SharedArrayBuffer`는 COOP/COEP 없으면 조용히 단일 스레드로 떨어진다.
- Vercel Functions 요청 본문 4.5MB 제한 → 나중에 유료층 업로드는 **Vercel을 우회**해 4080/R2로 직행.
- 도구 사이트는 스크래퍼가 wasm 자산을 긁어 대역폭을 태운다 → Vercel Firewall 레이트 리밋 필요.
- WebGPU 어댑터 VRAM은 데스크톱 1~4GB, 모바일은 그 이하. iOS Safari는 여전히 불안정.
